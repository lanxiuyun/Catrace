# 官网版本说明页与更新弹窗改造评估

> **状态：方案研究，未实施。** 本文根据当前仓库代码与官方 Web 平台资料评估「更新提醒从 GitHub commit 信息改为官网版本信息页」的产品/技术方案。官网是否已具备版本页、域名/部署方式、服务器响应头、客户端 WebView 版本与实际行为均尚未验证；涉及这些内容处均明确标注假设或待确认。

## 一、决策摘要

建议**把更新检测/下载与版本说明内容解耦**：继续由现有 Tauri updater `latest.json` 负责发现版本、下载 URL 和签名校验；官网负责可读、可维护的版本说明。客户端在检测到更新时以 `version` 作为稳定键，查找该版本页面或数据，并在独立的更新详情视图中呈现。

推荐分阶段采用：

1. **先做外链**：更新弹窗提供「查看版本说明」链接，在系统浏览器打开官网该版本页面；保留目前标题、更新操作及可用的 GitHub updater body 兜底。此方案不依赖官网允许 iframe，风险最低。
2. **验证嵌入可行性后再做内嵌**：先由官网提供专用、轻量、响应式的版本内容视图，并明确允许 Catrace 的嵌入来源；客户端用 iframe 展示，失败时显示本地兜底文案和外链。不要直接嵌完整官网导航页面。
3. **建立版本发布流程**：约定版本号、版本说明文件/数据 schema、页面 URL 永久规则及发布核对项；统一发布时机，避免客户端已发现版本而说明页尚未就绪。

关键结论：**版本号应当是映射主键，commit hash 不适合作为用户-facing 内容标识；iframe 的显示能力由官网 HTTP 安全响应头、客户端容器/CSP 与网络共同决定，不能仅靠客户端 HTML 保证。**

## 二、本地现状（仓库证据）

- [自动更新功能说明](README.md)记载：使用 Tauri `tauri-plugin-updater`；`latest.json` 位于 GitHub Release；启动后 3 秒异步检查一次；设置页也可手动检查；更新发现后出右下角橙色 Toast；检查失败只记日志、不阻断启动；下载后由 updater 校验签名。
- [Rust 更新实现](../../../src-tauri/src/update.rs)中 `GITHUB_LATEST_JSON` 指向 `lanxiuyun/Catrace/releases/latest/download/latest.json`；检查结果元数据包含 `current_version`、`version`、`body`、`raw_json`。即当前版本说明信息具有 updater body 来源，但该数据并不等于官网发布内容。
- [更新换源开发记录](../../devlog/2026-08-31-更新支持换源Toast也能选.md)说明客户端可在多个 GitHub 镜像/直连来源间检查与下载；官网说明页是另一条内容分发链路，不能替换或影响签名更新链路。
- [文档索引](../../manifest.yaml)把自动更新功能归在 `.agent/features/auto-update/`。因此本研究放在该目录作为现行功能的方案补充，不写入已清空的 `.agent/decisions/`。

**当前需求解释（假设）**：「从 GitHub commit 信息改为官网版本信息页」指更新提醒的可读变更说明由当前可能显示的 commit/updater body 转向官网按版本管理的内容；不是把安装包、签名或更新检测迁到官网。仓库现有文件未证实现有弹窗一定直接展示 commit 信息，需产品/实现负责人确认。

## 三、候选内容承载与显示方案比较

| 方案 | 内容维护/展示 | 优点 | 主要代价与风险 | 建议 |
|---|---|---|---|---|
| A. 只用 updater `body` | 发布时把 Markdown/文本写入 updater 元数据 | 客户端现有更新响应即可供内容，链路简单，镜像策略复用 | 内容长度、格式和图片能力有限；官网内容需另行同步；当前仓库未确认 body 实际格式/来源 | 可作离线/过渡兜底，不作为官网权威版本库 |
| B. 外链官网版本页 | 弹窗显示摘要/按钮，系统浏览器打开对应版本页 | 不受 iframe 禁止嵌入影响；网站可自由排版图片；失败隔离；简单且更安全 | 跳转打断桌面内阅读；需要联网/外部浏览器 | **第一阶段推荐** |
| C. iframe 内嵌官网完整页面 | 客户端嵌一个按版本定位的 URL | 用户不离开弹窗；官网内容可实时更新、支持富文本和图片 | `frame-ancestors`/`X-Frame-Options` 可能拒绝；跨域内容不可由父页面读取/改样式；网页变化可破坏弹窗体验；WebView 安全边界复杂 | 不直接内嵌完整站点 |
| D. iframe 内嵌专用精简内容页 | 官网维护适合窄视口的版本详情 endpoint/page，iframe 显示 | 兼顾统一维护与内嵌；可专门适配弹窗、图片、暗色/窄宽 | 官网要明确允许 Catrace 嵌入；要兼顾多平台 WebView；需要独立失败与兼容策略 | **嵌入验证通过后推荐** |
| E. 客户端渲染结构化版本数据 | 按 version 获取 JSON/Markdown 结构化内容，由本地 UI 渲染 | 样式一致、行为可控、可校验链接/图片域名；可实现缓存与本地兜底 | 要定义 schema、解析器、图片与安全策略；格式迭代增加客户端兼容成本 | 内容标准化且版本量增长后可评估 |

**建议目标形态：D + B + A 的分层兜底**。每个版本有官网权威说明；桌面内嵌只是一种呈现方式；链接始终可以外部打开；网络/嵌入失败不阻塞安装与升级。若维护资源有限，长期维持 B + A 比引入 iframe 更划算。

## 四、iframe 的约束、安全与兼容

### 4.1 页面是否能被嵌入，官网说了算

- 官网页面响应中的 CSP `frame-ancestors` 指定允许哪些父页面嵌入；设置为 `'none'` 即禁止任何嵌入，且会检查所有祖先上下文。`frame-ancestors` 必须通过 HTTP 响应头配置，不能用 `<meta>` 代替。来源：[MDN：CSP `frame-ancestors`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors)、[W3C CSP Level 3](https://w3c.github.io/webappsec-csp/#directive-frame-ancestors)。
- `X-Frame-Options: DENY` 会禁止嵌入，`SAMEORIGIN` 只允许同源祖先；因此官网若带这些响应头，即使客户端写了 `<iframe>` 也不能显示。现代策略应与 `frame-ancestors` 一并审核。来源：[MDN：X-Frame-Options](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Frame-Options)。
- **待验证**：需对准备使用的官网 URL 实测最终重定向后的 HTTP 响应头；GitHub Pages、自定义域、CDN/WAF 与最终部署设置可能不同。不能仅凭当前官网首页在浏览器可访问，就推断特定版本页可 iframe。

### 4.2 跨域样式和数据访问

- iframe 是独立嵌套浏览上下文。跨域同源策略会阻止父页面任意读取/修改子页面 DOM、样式和内容；父页面不能依赖 CSS 把官网内容强制改成符合弹窗的尺寸/主题。来源：[MDN：Same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy)、[WHATWG HTML iframe](https://html.spec.whatwg.org/multipage/iframe-embed-object.html#the-iframe-element)。
- 如需宿主与页面通信（例如内容高度、主题），必须由官网明确实现受控 `postMessage` 协议；接收端验证 `origin`、消息 schema 和目标窗口，不能把任意消息当作可信指令。建议优先固定 iframe 高度并在其内部滚动，避免增加通信协议。
- 官网版本内容及所引图片、链接属于外部可变内容；在宿主视觉上需明确来源（官网）并提供外部浏览器打开选项。只嵌入专用内容页面，不嵌后台管理、登录或无关交互页面。

### 4.3 sandbox 与权限最小化

`<iframe sandbox>` 可限制嵌入内容能力；MDN 将其描述为对框架内容增加限制，且 `allow` 属性用于权限策略（如摄像头、麦克风等）。默认应不授予脚本、表单、弹窗、下载等不需要的能力；仅在官网实现确有必要时逐项放开并评审。需要注意，sandbox 可能使页面依赖的脚本/导航/图片等行为失效，需实际测试。来源：[MDN：iframe 元素](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)、[WHATWG HTML iframe](https://html.spec.whatwg.org/multipage/iframe-embed-object.html#the-iframe-element)。

**安全建议**：限定固定 HTTPS 主机与版本 URL 模板，拒绝任意远程 URL；禁用不需要的 iframe 权限；对外链使用系统浏览器且仅允许已知 HTTPS URL；内容文案不承载更新包 URL/签名/命令。安装包仍由 Tauri updater 校验签名，不因页面内容而改变。

## 五、版本内容映射与官网发布管理

### 5.1 映射主键

建议以 updater 返回的 `version`（规范化为发布 tag 对应的版本字符串）作为唯一映射键，使用固定规则构造页面，例如：

- `https://<官网域名>/releases/<规范化版本号>`（版本级永久地址）；或
- 一个版本目录索引/manifest：`version -> 页面 URL / 内容状态`。

最终 URL 规则需结合官网路由确认，当前**不假定**官网已有该页面。避免用 `latest` 作为唯一说明地址：老客户端可能因缓存、延迟启动或网络不同看到较新版本页面；而本次发现版本是特定的 `version`。

要求：
- 页面 URL 在版本发布后保持稳定；不要复用路径表示不同版本。
- 未找到该版本时明确呈现「版本说明暂不可用」，退回 updater body/通用文字，并提供官网版本列表入口。
- 对预发布、回滚/重发、不同渠道（stable/beta）与不同语言设定命名规则；版本号相同但渠道内容不同要么不同路径，要么内容在页内明确渠道。
- 不允许远端页面控制「立即更新」动作、版本选择或安装包下载；这些由本地可信 updater 响应决定。

### 5.2 内容格式与图片

官网是最终样式控制者。若用 iframe：
- 单独设计窄宽、有限高度的嵌入模板；正文滚动，标题/版本/日期易扫读；避免依赖全站导航、复杂脚本和第三方追踪。
- 图片使用 HTTPS、响应式宽度、限定最大高度/宽度、设置替代文本；大图提供点击后外部查看；动图/视频慎用，避免弹窗高度被撑大或视觉干扰。
- 避免客户端硬编码网页 CSS 选择器；更新样式由官网部署，适配工作归官网模板负责人。
- 明确发布图片的可用性、大小、压缩和长期保留策略；断网时图片缺失不应导致正文不可读。

若采用结构化数据，由客户端渲染，则至少定义 `version`、`title`、`date`、`summary`、`sections`、`images`（alt/URL）、`links`、`locale` 与 schema version；验证 HTTPS 主机白名单、URL scheme、字段长度和内容类型。Markdown/HTML 原样注入 WebView 会引入 XSS 风险，不建议未经净化直接渲染。

### 5.3 发布时机与一致性

客户端已有启动后一次自动检查（[功能说明](README.md)），并可手动检查；说明页不可用不应影响更新检测/安装。要避免出现「新版本已对客户端可见，说明页尚未发布」的空窗，推荐顺序：

1. 编写并预览该版本官网说明（含图片、各语言、嵌入视图）；
2. 确认页面 URL 已发布且可访问，嵌入响应头符合要求；
3. 发布桌面版本与 updater `latest.json`；
4. 验证新旧版本客户端均可获取对应版本内容、安装签名链路正常；
5. 若发布流程需先产生 tag/构建物，可先以草稿或不公开方式预置说明页，再在 release 时启用；具体能力取决于官网 CMS/部署流程，**尚未验证**。

更理想的自动化是 CI 在发布前检查版本号/tag 与说明页面/manifest 存在性；当前仓库流程是否能对官网做该检查尚未验证，属于后续工程决策。

## 六、离线降级与旧版兼容

### 离线/弱网

- updater 检查本身失败：保持现状，只记录检查失败，不阻断启动（见 [功能说明](README.md)）。
- 新版已发现但说明页无法访问/被拒绝 iframe/图片失败：弹窗保留版本号、更新操作与简短默认提示；展示 updater `body`（若有）或「版本说明暂不可用」，提供外链按钮；不循环重试、不遮挡安装。
- 可选缓存最近成功获取的版本说明，提升短期离线体验；缓存应按版本号与语言区分，设合理过期/大小上限，标记可能非最新，且只作阅读缓存。**是否实现缓存待确认**。
- iframe `load` 事件不能可靠代表页面内容成功可用，浏览器对 iframe 加载错误事件有特殊处理；不可仅以 `onload` 断言 HTTP 成功。用超时显示降级只能改善 UX，不能准确判定页面状态。参见 [MDN：HTMLElement `load` event](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/load_event)。

### 旧版兼容

- 已发布的旧客户端不会自动获得新 iframe 功能；它们仍按原更新 UI/body 行为工作，除非专门通过更新升级客户端。
- 新客户端读取旧版本说明时，版本 URL 规则必须覆盖仍受支持的历史版本；找不到页面要兜底，不能使更新弹窗崩溃。
- 官网应保留已发布说明页，不把历史内容覆盖成 latest；对于未有专页的历史版本可以批量补齐，也可明确使用旧 updater body/归档链接。
- 如果切换字段/schema，先保持客户端向后兼容：例如新增可选 `releaseNotesUrl`/manifest，缺失时按版本模板生成；但最终字段是否放在 updater metadata、官网 manifest 或客户端固定模板，需要评估后定案。

## 七、维护成本与运营责任

| 责任 | 外链方案 | iframe 专页 | 结构化数据本地渲染 |
|---|---:|---:|---:|
| 每版本内容撰写 | 低/中 | 中 | 中 |
| 官网适配窄弹窗与图片 | 无需 | 每次模板变更需验收 | 无需（由客户端适配） |
| 发布一致性校验 | 建议做 | 必须做 | 必须做 |
| iframe 响应头/跨域兼容维护 | 无 | 必须 | 无 |
| 客户端解析/安全维护 | 低 | 低（只管理 iframe URL/降级） | 高（schema、渲染、净化） |
| 离线支持 | updater body/缓存 | 需额外兜底 | 可缓存，但需版本/语言策略 |
| 外部内容变更对旧客户端影响 | 页面本身可变 | 较高，旧客户端实时显示新样式 | 较低但要兼容 schema |

官网页面维护者需承诺：版本页长期不删、旧 URL 不改义；内容不依赖登录/地域限制；图片/资源持续可用；嵌入策略变更会通知客户端维护者。否则内嵌 iframe 将形成跨团队运行时依赖，维护成本高于外链。

## 八、推荐与分阶段落地

### 阶段 0：决策/探测，不写代码

- 确认官网域名、技术栈、部署者与现有版本发布机制。
- 明确版本内容是否允许被任何人公开访问、是否支持英文/多语言、历史版本保留策略。
- 实测目标页面的最终响应头、重定向、CSP、X-Frame-Options、TLS 与图片资源；在 Windows WebView2、macOS WKWebView（如支持）、Linux WebKitGTK（如支持）验证，具体平台支持范围需按当前发行版本确认。
- 确认用户是否必须在弹窗内阅读，还是外链即可满足需求。

### 阶段 1：低风险替换内容来源

- 官网建立版本级说明页，按 `version` 管理；先在弹窗提供外链入口。
- updater body 继续作为短摘要/离线兜底，更新检测、镜像、签名下载完全不动。
- 建立发布 checklist：官网页先就绪，随后公开 updater release；验证 URL 对应正确版本。

### 阶段 2：受控 iframe 试点

- 官网增加专用嵌入视图，明确 `frame-ancestors` 白名单并清理冲突的 X-Frame-Options；部署响应头需由官网负责人操作。
- 在一条版本上试点，固定 iframe 主机、sandbox、尺寸、滚动、超时与降级状态；默认关闭摄像头/麦克风/地理位置/弹窗等不必要能力。
- 试测常见窗口尺寸、缩放比例、暗色背景、图片失败、离线、HTTP 拒绝、重定向及旧版本；失败时外链始终可用。

### 阶段 3：常态化治理

- 将官网说明页存在性、版本号一致性、嵌入响应头/页面健康检查加入发布核对或 CI。
- 按真实使用反馈决定是否加入按版本本地缓存、结构化数据、语言选择与历史版本补录。
- 定期检查 iframe origin 白名单与权限清单；若维护投入过高，回退为外链，而非继续扩大 iframe 权限。

## 九、待确认问题

1. 「GitHub commit 信息」具体指哪个当前 UI 字段/数据来源？仓库能确认 updater 返回 `body`，未能确认 UI 目前怎样展示 commit。
2. 官网是否已存在版本信息页？期望正式域名、URL 规范和部署/内容所有者是谁？
3. 版本说明是否要求弹窗内显示，还是「查看官网说明」外链即可？
4. 官网是否能配置并长期维护 `Content-Security-Policy: frame-ancestors`；是否存在 CDN 或平台级 `X-Frame-Options` 冲突？
5. 目标平台及最低系统/WebView 版本是什么？是否需三平台同等支持？
6. 是否需要历史版本补齐、预发布渠道区分、多语言、图片视频以及本地缓存？
7. 官网发布与 GitHub Release 的先后顺序、失败回滚和 CI 校验由谁负责？
8. 内容是否允许第三方可见，是否包含隐私敏感或仅面向特定渠道的信息？
